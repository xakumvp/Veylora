# Архитектура Veylora

## Слои

```
React (frontend/src)                         Go (internal/)
───────────────────                          ──────────────
panels/*  ── stores (Zustand) ── services ──▶ app (Wails bindings)
                ▲                                  │
                └──── events (run:*, node:*, log:*)◀── engine ── nodes ── execution
                                                   │
                                                storage (SQLite)
```

- **Frontend** отвечает за интерфейс: холст (React Flow), Inspector, панели. Состояние живёт в четырёх Zustand-сторах:
  - `workspace` — проекты, Workflow, описания Nodes, настройки;
  - `editor` — граф, Undo/Redo, автосохранение;
  - `run` — статусы Nodes, логи, история, ошибки валидации;
  - `ui` — диалоги и уведомления.
- **Backend** исполняет Workflow, хранит данные и пишет журнал. Frontend вызывает методы `internal/app.App` (Wails bindings), а backend отвечает событиями Wails.

## Модель Workflow

`workflow.Document` — это JSON, который хранится в `workflows.workflow_json` и попадает в экспорт:

```json
{
  "schemaVersion": 1,
  "nodes": [{ "id": "…", "type": "http.request", "name": "…", "key": "http", "params": {}, "position": { "x": 0, "y": 0 } }],
  "edges": [{ "id": "…", "source": "…", "sourceHandle": "out", "target": "…", "targetHandle": "in" }],
  "viewport": { "x": 0, "y": 0, "zoom": 1 }
}
```

Порты (`inputs` / `outputs`) хранятся не в документе, а в `nodes.Definition` для каждого типа. Это единый источник правды для валидации на Go, проверки соединений на холсте и формы Inspector.

## Валидация (`internal/validation`)

`Structure` проверяет:
- версию схемы и лимиты (500 Nodes, 2000 Connections);
- уникальность ID и имён переменных, известные типы;
- ровно один Manual Trigger;
- существование Nodes и портов у каждого Connection, совпадение типа портов, отсутствие дублей и петель;
- отсутствие циклов (алгоритм Кана, путь цикла находится через DFS);
- предупреждение о Nodes, недостижимых от триггера.

`Params` проверяет параметры по `ParamSpec`: обязательность (с учётом `optionalWhen`), числа и диапазоны, значения select. Плюс специфичные правила Node, например схему URL.

Импорт требует `Structure`. Запуск требует `Structure` и `Params`. Редактор показывает и то и другое в реальном времени.

## Исполнение (`internal/engine`)

1. `Prepare` валидирует документ и строит топологический порядок. Среди готовых к запуску Nodes выбирается тот, что левее и выше на холсте, поэтому порядок предсказуем.
2. Все Nodes получают статус `WAITING`, триггер помечается активным.
3. Nodes обходятся по порядку:
   - неактивный Node получает `SKIPPED`;
   - активный выполняется (`RUNNING` → `SUCCESS` / `FAILED` / `CANCELLED`).
4. После успеха вывод публикуется в контекст под `node.key`. Активируются цели исходящих связей: все, если `Result.Branch` пуст, иначе только связи из порта с этим именем (так работает Condition).
5. При ошибке путь обрывается: потомки не активируются и получают `SKIPPED`. Общий статус запуска — `FAILED`.
6. При отмене контекста (Stop или закрытие приложения) текущий Node и все оставшиеся получают `CANCELLED`.

Такой подход даёт последовательное выполнение с ветвлением и слиянием веток без отдельного планировщика. Паника внутри Node перехватывается и превращается в `FAILED`.

`Manager` допускает несколько одновременных запусков разных Workflow (лимит в Settings) и не больше одного запуска на Workflow. Он отвечает за `Stop()`, а также за `Shutdown()`: тот отменяет запуск и ждёт его завершения (до 5 с), чтобы статус `CANCELLED` успел сохраниться в базу.

## Переменные (`internal/execution`)

- `Context` хранит выводы Nodes. Путь `http.body.items.0.name` проходит по картам и массивам.
- `ResolveString` подставляет значения в текст. Объекты сериализуются в JSON, отсутствующие переменные становятся пустой строкой.
- `ResolveValue` возвращает типизированное значение, если строка целиком состоит из одной переменной.
- `Redactor` запоминает значения секретов (заголовки и query с «чувствительными» именами, пароли в URL) и заменяет их на `••••••` в логах, ошибках и выводе, который уходит в GUI.

## Планировщик (`internal/scheduler`)

`Scheduler.Activate(workflowID, doc, allowedDirs)` проверяет и «взводит» все автоматические триггеры Workflow. Если хотя бы один триггер некорректен, не взводится ни один.

- **Cron**: следующий момент считается через `robfig/cron` в часовом поясе триггера.
- **Interval**: после перезапуска интервал продолжается от времени последнего срабатывания из таблицы `schedules`.
- **Schedule**: однократный запуск. Пропущенное время (компьютер был выключен) не выполняется задним числом.
- **File Watcher**: работает на `fsnotify`. Каталог проверяется через `ResolveAllowedDir` (абсолютный путь, разрешение символических ссылок, вхождение в разрешённый корень). События по одному файлу склеиваются за 500 мс, символические ссылки при рекурсивном обходе не обходятся.
- **Startup** срабатывает один раз после восстановления расписаний при старте.

Срабатывание вызывает `App.fireTrigger`: он загружает **последнюю сохранённую** версию Workflow и запускает её через `Manager`. Если предыдущий запуск того же Workflow ещё идёт, срабатывание пропускается, а в GUI уходит событие `trigger:skipped`.

Флаг активности хранится в `workflows.active`. При старте `restoreSchedules` заново взводит все активные Workflow. Если взвести не удаётся (например, каталог больше не разрешён), Workflow отключается и пользователь получает уведомление.

## Обработка ошибок Node

`workflow.NodeSettings`:
- `retry` — число попыток, пауза, exponential backoff, максимальная пауза;
- `timeoutSec` — таймаут одной попытки;
- `onError` — поведение при ошибке.

| `onError` | Статус Node | Дальше | Статус запуска |
| --- | --- | --- | --- |
| `stop` (по умолчанию) | FAILED | путь обрывается | FAILED |
| `continue` | FAILED (обработано) | основной выход | не влияет |
| `error_output` | FAILED (обработано) | выход `error` | не влияет |

Таймаут Workflow (`settings.timeoutSec`) отменяет запуск со статусом `TIMEOUT`. Node `Stop Workflow` завершает запуск сразу, а оставшиеся Nodes получают `SKIPPED`.

## События

| Событие | Payload | Когда |
| --- | --- | --- |
| `run:started` | `RunEvent` | начало запуска |
| `node:status` | `NodeEvent` (status, branch, error, output, duration) | каждая смена статуса Node |
| `log:entry` | `Log` | каждая строка лога |
| `run:finished` | `RunEvent` (status, duration, error) | конец запуска |
| `scheduler:changed` | ID Workflow | изменилось состояние автоматизации |
| `trigger:skipped` | workflowId, nodeId, reason | срабатывание пропущено (уже выполняется, лимит) |

Вывод Node, который отправляется в GUI, обрезается до 256 КБ. В контексте переменных остаётся полная версия.

## Хранение (`internal/storage`)

SQLite через чистый Go-драйвер `modernc.org/sqlite` (CGO и компилятор C не нужны). Используются WAL, `foreign_keys` и одно соединение. Миграции версионируются через `PRAGMA user_version`.

Таблицы: `projects`, `workflows`, `executions`, `execution_logs`, `settings`. Удаление каскадное. Для каждого Workflow хранятся последние N запусков (настраивается). При старте запуски, оставшиеся в `RUNNING` после сбоя, помечаются `CANCELLED`.
